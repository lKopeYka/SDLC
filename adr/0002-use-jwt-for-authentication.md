# Использование JWT для аутентификации и авторизации

## Контекст и постановка задачи
Приложению CineShelf требуется разграничение прав доступа (гость, пользователь, администратор) согласно требованию REQ-FUNC-003. Серверная часть представляет собой REST API, которое будет взаимодействовать с фронтендом. Необходимо выбрать stateless-механизм аутентификации, так как мы планируем использовать монолитную архитектуру без сложных кластеров сессий.

## Драйверы решения
* **Безопасность:** Пароли должны храниться в виде BCrypt-хэша (REQ-SEC-001), а передача данных — по HTTPS.
* **Масштабируемость:** Отсутствие состояния (stateless) на сервере упрощает развертывание.
* **Простота интеграции:** Легкость передачи токена в заголовках HTTP-запросов.

## Рассмотренные варианты
* **Вариант 1: Серверные сессии (Spring Session + Redis/БД).** Сервер хранит состояние сессии, клиент получает Cookie.
* **Вариант 2: JWT (JSON Web Tokens).** Сервер выдает подписанный токен, который клиент отправляет в заголовке `Authorization`.

## Итог решения
Выбранный вариант: **«JWT (JSON Web Tokens)»**, потому что он идеально подходит для REST API, не требует хранения состояния на сервере (stateless) и легко масштабируется.

### Последствия
* **Хорошо, потому что** серверу не нужно обращаться к базе данных или Redis для проверки каждой сессии.
* **Плохо, потому что** отозвать (аннулировать) выданный JWT токен до истечения срока его действия сложнее (требуется blacklist).

### Подтверждение
Проверка токенов будет осуществляться через Spring Security Filter Chain. Наличие роли `ROLE_ADMIN` в токене будет проверяться при доступе к методам `POST /api/v1/movies`.
