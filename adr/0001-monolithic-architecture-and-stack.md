# Выбор монолитной архитектуры и технологического стека для CineShelf

## Контекст и постановка задачи

Согласно SRS, CineShelf — это web-приложение для ведения коллекции фильмов. Требования обязывают использовать Java (Spring Boot) для серверной части и реляционную СУБД (предпочтительно PostgreSQL). 

Разработка ведется силами 1-2 студентов в рамках учебного курса. Необходимо создать работающий MVP в сжатые сроки, обеспечив при этом выполнение нефункциональных требований по производительности (REQ-PERF-002) и надежности (REQ-REL-001).

**Проблема:** Какую архитектурную модель и набор технологий выбрать для обеспечения быстрой, но качественной разработки MVP без избыточного усложнения инфраструктуры?

## Драйверы решения

* **Скорость разработки:** Ограниченное время на выполнение лабораторных работ требует минимизации времени на настройку инфраструктуры.
* **Технологические ограничения:** Жесткие требования SRS по использованию Java/Spring Boot.
* **Компетенции команды:** Команда владеет Java и основами реляционных БД, но не имеет опыта промышленной эксплуатации микросервисов.
* **Сложность развертывания:** Требование REQ-INST-001 обязывает разворачивать систему простой командой `docker compose up`.

## Рассмотренные варианты

* **Вариант 1: Микросервисная архитектура.** Выделение каталога, оценок и пользователей в отдельные сервисы.
* **Вариант 2: Монолитная слоистая архитектура (Layered Monolith).** Единое приложение, разделенное на логические слои (Controller, Service, Repository).

## Итог решения

Выбранный вариант: **«Монолитная слоистая архитектура»**, потому что для данного объема функционала и размера команды она обеспечивает наилучший баланс между скоростью разработки и поддерживаемостью. Микросервисы на данном этапе приведут к неоправданным накладным расходам на DevOps.

### Последствия

* **Хорошо, потому что** упрощается процесс отладки, развертывания и тестирования. Вся логика находится в одном репозитории и запускается в одном контейнере.
* **Хорошо, потому что** строгое разделение на слои (Service, Repository) позволяет изолировать бизнес-логику расчетов оценок от контроллеров и БД (выполнение REQ-MAINT-002).
* **Плохо, потому что** при необходимости горизонтального масштабирования придется масштабировать все приложение целиком, даже если нагрузка возрастет только на модуль каталога.
* **Нейтрально, потому что** в будущем, при росте проекта, наиболее нагруженные модули можно будет вынести в отдельные сервисы (паттерн Strangler Fig).

### Подтверждение

Соблюдение слоистой архитектуры будет проверяться на этапе Code Review (запрет на прямые вызовы репозиториев из контроллеров). Для автоматизации можно использовать библиотеку ArchUnit на этапе CI.

## Плюсы и минусы вариантов

### Вариант 1: Микросервисная архитектура

* Хорошо, потому что обеспечивает независимое масштабирование каждого сервиса.
* Нейтрально, потому что требует написания межсервисных контрактов (gRPC/REST) и настройки брокеров сообщений.
* Плохо, потому что резко возрастает сложность инфраструктуры (Service Discovery, API Gateway, Distributed Tracing).
* Плохо, потому что значительно замедляет выход MVP из-за настройки DevOps.

### Вариант 2: Монолитная слоистая архитектура

* Хорошо, потому что позволяет быстро начать разработку и сосредоточиться на бизнес-логике.
* Хорошо, потому что легко упаковывается в один Docker-образ (выполнение REQ-INST-001).
* Нейтрально, потому что кодовая база со временем может стать связанной (High Coupling), если не следить за границами слоев.
* Плохо, потому что требует дисциплины от разработчиков для поддержания модульности.

## Дополнительная информация

Решение принято на этапе проектирования (ЛР4). При превышении нагрузки на какой-либо из модулей (например, `StatsService` при большом количестве данных) решение может быть пересмотрено в сторону выноса модуля в отдельный сервис.

**Связанные требования SRS:** `REQ-INST-001`, `REQ-PERF-002`, `REQ-MAINT-002`.
**Связанные представления SDD:** View 002 (Композиция), View 003 (Логическое).
