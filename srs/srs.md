## 1. Введение

Документ определяет, ЧТО должно делать приложение CineShelf, и не описывает, КАК оно будет реализовано. Он предназначен для заказчика, разработчиков и тестировщиков.

### 1.1 Назначение документа

Спецификация требований к ПО (SRS) фиксирует согласованный с заказчиком набор бизнес-, функциональных и нефункциональных требований к CineShelf версии 0.1. Заказчик по ней проверяет, что его ожидания учтены, разработчики используют её как исходные данные для проектирования, а тестировщики составляют по критериям приёмки тесты. Документ хранится в репозитории проекта под контролем версий.

### 1.2 Область применения продукта

CineShelf — web-приложение для людей, которые смотрят фильмы и хотят вести личную коллекцию. Пользователь просматривает общий каталог с жанрами и средними оценками, добавляет фильмы в личный «План к просмотру», отмечает просмотренное, ставит оценки и видит свою статистику. Администратор наполняет каталог и поддерживает справочник жанров. Бизнес-цель — помочь не терять фильмы, которые хотелось посмотреть, и не пересматривать случайно уже виденные.

В область релиза входят: учётные записи и роли; каталог фильмов с жанрами; план к просмотру; отметка просмотра; оценки и средняя оценка; личная статистика. Вне области текущего релиза: рекомендации, комментарии и общение между пользователями, онлайн-просмотр, мобильные приложения.

### 1.3 Определения, акронимы и сокращения

| Термин | Определение |
|--------|-------------|
| SRS | Software Requirements Specification — спецификация требований к программному обеспечению. |

| План к просмотру | Личный список фильмов, которые пользователь собирается посмотреть. |

## 2. Обзор продукта

### 2.1 Перспектива продукта

CineShelf — новый самостоятельный web-продукт. Клиентская часть работает в браузере, серверная часть пишется на Java с использованием Spring Boot, данные хранятся в реляционной базе. Продукт не является стриминговым сервисом и не хранит видеоматериалы. Соглашение об уровне обслуживания (SLA) не предусмотрено.

```
Гость / Пользователь / Администратор ──► Web-интерфейс ──► Сервер CineShelf (Java, Spring Boot) ──► База данных
```

### 2.2 Функции продукта

- Регистрация, вход и разграничение ролей (гость, пользователь, администратор).
- Просмотр, поиск и фильтрация каталога фильмов с жанрами и средними оценками.
- Личный «План к просмотру» с приоритетами и заметками.
- Отметка фильма просмотренным и личная оценка от 1 до 10.
- Автоматический расчёт средней оценки и топ-10 фильмов каталога.
- Личная статистика: число просмотренных, средняя оценка, любимые жанры.
- Управление каталогом и справочником жанров (администратор).

### 2.3 Ограничения продукта

- Серверная часть должна быть написана на Java с использованием Spring Boot (обязательное, по заданию заказчика).
- Продукт должен быть web-приложением и работать в современных браузерах (обязательное).
- Данные должны храниться в реляционной СУБД; предпочтительна PostgreSQL (предпочтительное).
- Интерфейс и документация — на русском языке.
- Изменять каталог и справочник жанров может только роль «Администратор» (обязательное, см. REQ-FUNC-003).
- Внешний сервис с данными о фильмах не является обязательной частью версии 1.0.

### 2.4 Характеристики пользователей

| Класс | Описание | Частота и цели |
|-------|----------|----------------|
| Гость | Посетитель без учётной записи | Эпизодически: посмотреть каталог и карточки фильмов |
| Пользователь | Зарегистрированный любитель кино без специальной технической подготовки; пользуется с телефона и компьютера | Несколько раз в неделю: пополнить план, отметить просмотр, поставить оценку, посмотреть статистику |
| Администратор | Владелец или редактор каталога | Регулярно: добавление и изменение фильмов, ведение справочника жанров |

### 2.5 Допущения и зависимости

| Допущение / зависимость | Влияние, если не выполняется |
|--------------------------|------------------------------|
| Администратор своевременно наполняет каталог фильмами | Пользователям нечего добавлять в план; ценность продукта падает |
| У каждого пользователя есть адрес электронной почты | Регистрация невозможна |
| Для внешнего сервиса данных о фильмах выбран поставщик и проверены условия доступа | Импорт переносится в следующий релиз (REQ-INT-007) |
| Пользователи ставят оценки добросовестно | Средняя оценка и топ-10 теряют смысл; потребуется модерация (см. открытые вопросы) |

## 3. Требования

Формат идентификатора: REQ-[ОБЛАСТЬ]-[NNN]. Приоритет: M — обязательно, S — желательно, C — возможно. Метод верификации по умолчанию — «Тест»; иные методы указаны в разделе 4.

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательские интерфейсы

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-INT-001 | Система должна предоставлять web-интерфейс на русском языке с адаптивной вёрсткой для ширины окна от 360 до 1920 px. | M | При ширине 360, 768, 1366 и 1920 px нет горизонтальной прокрутки; каталог, поиск и кнопка добавления в план доступны без дополнительных действий. |
| REQ-INT-002 | Система должна после каждого действия пользователя (добавление в план, отметка просмотра, оценка) показывать результат операции и актуальное состояние фильма. | M | После операции на экране виден новый статус фильма, обновлённая оценка или причина отказа. |
| REQ-INT-003 | Система должна предоставлять фильтры каталога по жанру, году выпуска и средней оценке, сортировку и поиск по названию. | S | После применения фильтра в списке остаются только подходящие фильмы; сброс возвращает полный каталог. |
| REQ-INT-004 | Карточка фильма в каталоге должна показывать название, год, жанры, среднюю оценку и личный статус пользователя («в плане», «просмотрен», «нет»). | M | Каждая карточка содержит все указанные поля; средняя оценка совпадает с данными в БД. |
| REQ-INT-005 | Ошибки ввода должны сопровождаться текстовым сообщением рядом с полем, а пустые списки — подсказкой, что делать дальше. | S | Некорректная форма не отправляется и показывает причину; у нового пользователя пустой «План к просмотру» содержит ссылку на каталог. |

#### 3.1.2 Аппаратные интерфейсы

Не применимо: система не взаимодействует с аппаратурой напрямую.

#### 3.1.3 Программные интерфейсы

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-INT-006 | Система должна предоставлять REST API в формате JSON, описанное спецификацией OpenAPI 3.0. | M | Спецификация доступна по адресу /v3/api-docs и проходит валидацию без ошибок; все операции интерфейса выполнимы через API. |
| REQ-INT-007 | Система может импортировать данные о фильмах из внешнего сервиса (OMDb или TMDB) по названию. | C | По названию находится карточка фильма; администратор подтверждает импорт, поля заполняются автоматически. |
| REQ-INT-008 | При недоступности внешнего сервиса основные функции (каталог, план, оценки) должны оставаться работоспособными. | S | При эмуляции сбоя внешнего сервиса пользователь просматривает каталог, ведёт план и ставит оценки. |

### 3.2 Функциональные требования

##### Учётные записи и роли

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-001 | Система должна позволять посетителю зарегистрироваться по имени, адресу электронной почты и паролю (не менее 8 символов, буква и цифра). | M | Корректные данные создают учётную запись; повторный email и слабый пароль отклоняются с сообщением. |
| REQ-FUNC-002 | Система должна предоставлять вход и выход; срок действия сессии должен быть ограничен (не более 7 суток). | M | После выхода личные страницы требуют повторного входа; по истечении 7 суток вход запрашивается заново. |
| REQ-FUNC-003 | Система должна поддерживать три роли (гость, пользователь, администратор) и ограничивать управление каталогом ролью администратора. | M | Запрос гостя или пользователя на создание или изменение фильма отклоняется с кодом 403; гость не видит личные разделы. |

##### Каталог фильмов

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-004 | Система должна показывать каталог фильмов постранично (по 20 записей) всем ролям, включая гостя. | M | Каталог открывается без входа; на странице не более 20 фильмов, доступен переход между страницами. |
| REQ-FUNC-005 | Система должна показывать карточку фильма с названием, годом, длительностью, жанрами, описанием, средней оценкой и числом оценок. | M | Открытие карточки показывает все перечисленные поля; для фильма без оценок выводится «Нет оценок». |
| REQ-FUNC-006 | Администратор должен добавлять фильм с названием, годом выпуска, длительностью, описанием и жанрами. | M | Новый фильм сразу отображается в каталоге; длительность — целое число минут больше нуля, указан хотя бы один жанр. |
| REQ-FUNC-007 | Администратор должен изменять фильм и переводить его в архив. | M | Изменения видны в каталоге; архивный фильм скрыт из каталога и недоступен для добавления в план. |
| REQ-FUNC-008 | Администратор должен вести справочник жанров: добавлять и переименовывать жанры; жанр, назначенный фильмам, удалять нельзя. | M | Попытка удалить используемый жанр отклоняется с сообщением; переименование отображается во всех карточках. |
| REQ-FUNC-009 | Система не должна позволять создать фильм с тем же названием и годом выпуска, что у уже существующего. | M | При попытке добавить дубликат показывается сообщение со ссылкой на существующую карточку. |

##### План к просмотру

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-010 | Пользователь должен добавлять фильм из каталога в личный «План к просмотру» одним действием. | M | После нажатия фильм появляется в плане, статус в карточке меняется на «в плане». |
| REQ-FUNC-011 | Система не должна позволять добавить в план фильм, который уже в плане или отмечен просмотренным. | M | Повторная попытка отклоняется с понятной причиной, дубликат в плане не создаётся. |
| REQ-FUNC-012 | Пользователь должен видеть свой план и удалять из него фильмы. | M | Список показывает название, год, жанры и дату добавления; удалённый фильм исчезает из плана и возвращает статус «нет». |
| REQ-FUNC-013 | Пользователь должен назначать фильму в плане приоритет (высокий, средний, низкий) и добавлять короткую заметку. | S | Приоритет и заметка сохраняются и отображаются в плане; план можно отсортировать по приоритету. |

##### Просмотр, оценки и статистика

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-014 | Пользователь должен отмечать фильм просмотренным с указанием даты; при этом фильм автоматически удаляется из плана. | M | После отметки фильм отображается в списке просмотренных с датой, из плана пропадает. |
| REQ-FUNC-015 | Пользователь должен ставить просмотренному фильму личную оценку от 1 до 10 и изменять её. | M | Допустимы только целые значения 1–10; вторая оценка того же фильма заменяет первую. |
| REQ-FUNC-016 | Система должна автоматически вычислять среднюю оценку фильма и число оценок. | M | Для тестового набора оценок среднее (с округлением до 0,1) совпадает с ручным расчётом и пересчитывается после изменения оценки. |
| REQ-FUNC-017 | Пользователь может оставить к своей оценке текстовый отзыв длиной до 1000 символов, видимый только ему. | S | Отзыв сохраняется и отображается в личном списке; другие пользователи его не видят. |
| REQ-FUNC-018 | Пользователь должен видеть список просмотренных фильмов с датой и личной оценкой и фильтровать его по жанру и оценке. | S | Фильтр оставляет только подходящие записи; сортировка по дате просмотра выполняется от новых к старым. |
| REQ-FUNC-019 | Система должна показывать пользователю личную статистику: число просмотренных фильмов, среднюю личную оценку и три самых частых жанра. | S | Для тестового набора записей значения статистики совпадают с ручным расчётом. |
| REQ-FUNC-020 | Система должна показывать в каталоге топ-10 фильмов по средней оценке (учитываются фильмы не менее чем с тремя оценками). | S | Топ содержит не более десяти фильмов, отсортированных по убыванию средней оценки; фильмы с менее чем тремя оценками исключены. |
| REQ-FUNC-021 | Система может экспортировать личную коллекцию (план и просмотренные) в файл CSV. | C | Файл открывается в табличном редакторе, содержит название, год, статус, дату и оценку каждого фильма. |

### 3.3 Качество обслуживания

#### 3.3.1 Производительность

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-PERF-001 | Страница каталога должна загружаться не более чем за 3 секунды при 10 000 фильмов в БД. | S | Среднее из 20 измерений не превышает 3 с. |
| REQ-PERF-002 | Операции добавления в план и выставления оценки должны завершаться не более чем за 1 секунду при 50 одновременных запросах. | M | 95-й процентиль не превышает 1 с; дубликатов в плане нет. |
| REQ-PERF-003 | Поиск по названию должен возвращать результат не более чем за 2 секунды. | S | Среднее из 20 запросов по каталогу в 10 000 фильмов не превышает 2 с. |

#### 3.3.2 Безопасность

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-SEC-001 | Пароли должны храниться только в виде хэша BCrypt со стоимостью не ниже 10. | M | В БД отсутствуют пароли в открытом виде; параметр стоимости в хэше не меньше 10. |
| REQ-SEC-002 | Система должна передавать данные между клиентом и сервером только по HTTPS (TLS 1.2 и выше). | M | HTTP-запрос перенаправляется на HTTPS; сканер не обнаруживает поддержки TLS ниже 1.2. |
| REQ-SEC-003 | Пользователь должен иметь доступ только к собственным плану, оценкам и отзывам; обращение к чужим личным данным не допускается. | M | Автотест: пользователь A запрашивает по id запись пользователя B — всегда отказ (404 или 403). |
| REQ-SEC-004 | Система должна проверять вводимые данные на стороне сервера: оценку (1–10), год выпуска (1888 – текущий год + 5), длительность и длину текстов. | M | Некорректный ввод отклоняется с сообщением и не вызывает сбоя. |
| REQ-SEC-005 | Журналы не должны содержать пароли, токены и секреты внешних сервисов. | S | Поиск по журналу за сутки не находит паролей и токенов. |

#### 3.3.3 Надёжность

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-REL-001 | Система должна хранить не более одной оценки пользователя на фильм и корректно пересчитывать среднюю оценку при одновременных запросах. | M | При 100 одновременных оценках одного фильма разными пользователями среднее и число оценок совпадают с контрольным расчётом. |
| REQ-REL-002 | Система должна корректно обрабатывать сетевые ошибки без аварийного завершения. | S | При обрыве соединения пользователь видит сообщение, приложение продолжает работу, данные не искажаются. |
| REQ-REL-003 | При архивировании фильма его записи в планах и оценки должны сохраняться и оставаться согласованными. | M | После архивирования фильм исчезает из каталога, но остаётся в списках просмотренных пользователей с прежними оценками; средняя оценка не меняется. |

#### 3.3.4 Доступность

Отдельные требования к доступности не заданы: SLA не предусмотрен (см. 2.1).

#### 3.3.5 Наблюдаемость

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-OBS-001 | Система должна журналировать создание, изменение и архивирование фильмов администратором (время, событие, технический идентификатор). | S | Журнал содержит три указанных поля для каждого события; персональные данные в нём отсутствуют. |

### 3.5 Проектирование и реализация

#### 3.5.1 Установка

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-INST-001 | Система должна разворачиваться командой docker compose up (приложение и PostgreSQL); настройки и секреты передаются переменными окружения. | M | На чистой машине с Docker приложение доступно не позднее чем через 5 минут; в репозитории нет паролей и токенов. |

#### 3.5.2 Сборка и поставка

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-BUILD-001 | Система должна собираться Maven в исполняемый JAR (Java LTS) и образ Docker; для каждого pull request CI выполняет сборку и тесты. | S | Проверка GitHub Actions в pull request проходит; сборка воспроизводима. |

#### 3.5.3 Распределение

Система разворачивается как один экземпляр приложения и одна БД; горизонтальное масштабирование в текущем релизе не требуется.

#### 3.5.4 Сопровождаемость

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-MAINT-001 | Исходный код и документация должны храниться в Git; изменения требований проходят через отдельную ветку и pull request. | S | В истории есть ветка, pull request и проверяемые коммиты. |
| REQ-MAINT-002 | Модуль оценок и расчёта средней оценки должен быть независим от web-слоя, а его тестовое покрытие — не менее 80 % строк. | S | Отчёт покрытия (JaCoCo) для модуля оценок показывает не менее 80 %. |

#### 3.5.5 Повторное использование

Модуль оценок отделяется от web-слоя, чтобы правила расчёта средней оценки можно было применять и в других клиентах.

#### 3.5.6 Переносимость

Система должна работать на любой ОС, где есть Docker или JDK соответствующей LTS-версии; привязка к конкретному облачному провайдеру не допускается.

#### 3.5.7 Стоимость

Разработка и размещение не требуют затрат: используется бесплатное ПО и учебная инфраструктура.

#### 3.5.8 Сроки

Сроки определяются графиком курса «Жизненный цикл разработки ПО»: SRS (лабораторная работа № 3) — октябрь 2026; MVP 0.1 — по графику следующих лабораторных работ; точные даты уточняются у преподавателя.

#### 3.5.9 Доказательство концепции

До полной реализации проверяется прототип расчёта средней оценки: при 100 одновременных оценках одного фильма результат совпадает с контрольным расчётом (REQ-REL-001). Результат определяет выбор способа хранения агрегатов в БД.

#### 3.5.10 Управление изменениями

Работа ведётся в ветках Git с обязательным pull request и ревью; версии нумеруются по SemVer; изменения требований записываются в историю изменений документа.

### 3.6 ИИ/МО

Не применимо: в версии 1.0 не используются обучаемые модели; рекомендации фильмов вынесены за рамки релиза.
