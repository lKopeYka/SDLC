## 1. Введение

### 1.1 Назначение документа
Данный документ (Software Design Description, SDD) описывает архитектуру и внутреннее устройство программного обеспечения CineShelf. Документ предназначен для команды разработчиков (архитекторов, программистов, тестировщиков) и служит руководством к действию при реализации системы. SDD базируется на утвержденной спецификации требований к ПО (SRS).

### 1.2 Область применения
Документ описывает проектирование первой версии продукта (MVP 0.1). Система представляет собой web-приложение для управления личной коллекцией фильмов, включающее общий каталог, личный план к просмотру, выставление оценок и просмотр статистики. 
В область применения SDD **входят**: архитектура приложения, модель данных, REST API и ключевые сценарии взаимодействия компонентов. 
**Не входят**: детальное проектирование пользовательского интерфейса (описано в макетах SRS) и инфраструктура CI/CD (описана в репозитории).

### 1.3 Определения, акронимы и сокращения

| Term | Definition |
|------|------------|
| API | Application Programming Interface — программный интерфейс приложения |
| SRS | Software Requirements Specification — спецификация требований к ПО |
| SDD | Software Design Description — документ описания дизайна ПО |
| ADR | Architectural Decision Record — протокол архитектурного решения |
| REST | Representational State Transfer — архитектурный стиль взаимодействия компонентов в сети |
| JPA | Java Persistence API — спецификация API для управления сохранением данных |
| DTO | Data Transfer Object — объект для передачи данных между слоями |

## 2. Обзор дизайна

### 2.1 Задачи стейкхолдеров

| Стейкхолдер | Задачи (Concerns) | Как адресуется в дизайне |
|---|---|---|
| **Разработчики** | Понятная структура кода, изоляция бизнес-логики от БД | Выбрана слоистая архитектура (Controller-Service-Repository). |
| **Заказчик** | Быстрый выход MVP, минимальные затраты | Использование Spring Boot и монолитной архитектуры для ускорения разработки. |
| **Администратор БД** | Целостность данных | Проектирование реляционной схемы с внешними ключами и ограничениями (п. 3.2). |
| **Тестировщики** | Проверяемость требований | Четкие контракты REST API и разделение на слои упрощают написание автотестов. |

### 2.2 Выбранные точки зрения
Для описания архитектуры выбраны следующие точки зрения:
* **Context (Контекст)** — для определения границ системы.
* **Composition (Композиция)** — для описания подсистем и слоев.
* **Information (Информация)** — для описания модели данных БД.
* **Interface (Интерфейс)** — для описания REST API.
* **Deployment (Развертывание)** — для понимания инфраструктуры.

## 3. Проектные представления

### View 001: Контекст системы
* **ID**: 001-Context
* **Title**: Границы системы CineShelf
* **Viewpoint**: Context
* **Representation**: CineShelf является самостоятельным web-приложением. Пользователи (Гость, Авторизованный пользователь, Администратор) взаимодействуют с системой через браузер. В перспективе система может обращаться к внешним API (OMDb/TMDB) для импорта данных (требование REQ-INT-007), но в MVP эта интеграция не реализуется.
* **More Information**: Соответствует разделу 2.1 SRS «Перспектива продукта».

### View 002: Композиция (Архитектурные слои)
* **ID**: 002-Composition
* **Title**: Слоистая архитектура приложения
* **Viewpoint**: Composition
* **Representation**: Приложение использует монолитную слоистую архитектуру (Layered Architecture). 
  * `Web Layer` (Controllers) — принимает HTTP-запросы, валидирует DTO.
  * `Service Layer` (Services) — содержит бизнес-логику (расчет средних оценок, проверка прав, ведение плана).
  * `Data Access Layer` (Repositories) — взаимодействует с БД через Spring Data JPA.
* **More Information**: Связано с ADR 0001.

### View 003: Логическое представление (Компоненты)
* **ID**: 003-Logical
* **Title**: Основные компоненты системы
* **Viewpoint**: Logical
* **Representation**: 
  * `AuthService` — аутентификация и выдача JWT.
  * `CatalogService` — CRUD операции с фильмами и жанрами.
  * `WatchlistService` — управление личным планом пользователя.
  * `RatingService` — выставление оценок и пересчет среднего балла (реализует REQ-REL-001).
  * `StatsService` — сбор статистики по просмотренным фильмам.
* **More Information**: Реализует функциональные требования REQ-FUNC-001 – REQ-FUNC-021.

### View 004: Информация (Модель данных)
* **ID**: 004-Information
* **Title**: Схема базы данных (ER-модель)
* **Viewpoint**: Information
* **Representation**: Реляционная модель данных (PostgreSQL).
  * **users**: `id` (PK), `email` (UQ), `password_hash`, `role`, `name`.
  * **movies**: `id` (PK), `title`, `release_year`, `description`, `is_archived` (boolean).
  * **genres**: `id` (PK), `name` (UQ).
  * **movie_genres**: `movie_id` (FK), `genre_id` (FK). Составной PK.
  * **watchlist_entries**: `id` (PK), `user_id` (FK), `movie_id` (FK), `priority` (enum), `note`, `added_at`, `status`.
  * **ratings**: `id` (PK), `user_id` (FK), `movie_id` (FK), `value` (1-10), `review`, `watched_at`. Уникальный индекс по (`user_id`, `movie_id`).
* **More Information**: Обеспечивает требования REQ-FUNC-004 - REQ-FUNC-016, REQ-REL-001.

### View 005: Интерфейс (REST API)
* **ID**: 005-Interface
* **Title**: Спецификация программных интерфейсов
* **Viewpoint**: Interface
* **Representation**: Система предоставляет REST API (формат JSON), документированный через OpenAPI 3.0 (Swagger). Основные эндпоинты:
  * `POST /api/v1/auth/login` — получение JWT токена.
  * `GET /api/v1/movies` — постраничный список фильмов (фильтры: жанр, год).
  * `POST /api/v1/movies` — добавление фильма (только Admin).
  * `GET /api/v1/watchlist` — получение плана к просмотру текущего пользователя.
  * `POST /api/v1/watchlist/{movieId}` — добавление в план.
  * `POST /api/v1/ratings/{movieId}` — выставление оценки.
* **More Information**: Реализует REQ-INT-006.

### View 006: Развёртывание
* **ID**: 006-Deployment
* **Title**: Физическое развертывание MVP
* **Viewpoint**: Deployment
* **Representation**: Приложение поставляется в виде Docker-образов. Используется `docker-compose`, состоящий из двух сервисов:
  1. `app` — Java Spring Boot приложение (порт 8080).
  2. `db` — PostgreSQL (порт 5432).
  Взаимодействие происходит по внутренней сети Docker.
* **More Information**: Соответствует REQ-INST-001.

## 4. Решения

* **ID**: 001-Architecture
* **Title**: Выбор монолитной архитектуры на базе Spring Boot
* **Context**: Необходимо реализовать MVP в сжатые сроки (по графику учебного курса), команда состоит из 1-2 разработчиков. Микросервисы потребуют слишком много времени на настройку инфраструктуры.
* **Options**: 1. Микросервисная архитектура. 2. Монолит со слоистой структурой.
* **Outcome**: Выбран вариант «Монолит со слоистой структурой», так как он обеспечивает достаточную модульность и скорость разработки.
* **More Information**: Детали описаны в `docs/adr/0001-architecture.md`.
